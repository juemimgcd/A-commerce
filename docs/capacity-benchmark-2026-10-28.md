# 2026-10-28 本机读写分离容量测试

## 结论

当前两个普通 API 进程下，未缓存商品查询的低延迟工作点约为 400 RPS；固定比例混合 HTTP 请求在 500 RPS、120 秒内全部成功。两者均不是生产容量承诺，不能外推到 50,000 RPS。混合测试仍有入口限流降级和支付后台待处理任务，未通过完整业务验收。

主要瓶颈是 API 进程 CPU/请求处理及饱和后的连接等待；本轮数据库节点没有先耗尽 CPU。读写分离明显卸载了主库，但未提高本轮端到端吞吐。

## 环境与方法

- MacBookPro18,4，主机 10 核、32 GiB；Docker 共用 10 CPU、约 7.75 GiB，所有 HA 服务在同一个宿主机。
- 10,000 商品、1,000 个种子用户，初始历史订单为 0；非百万历史订单规模。
- 两个普通 API 容器，各 1 个 Uvicorn 进程，各 5 条主库连接、5 条只读连接；另有回调 API、worker、PostgreSQL 一主两副本、Redis、RabbitMQ 和监控。
- 独立 Compose 项目，放宽单发压 IP 的入口限流，业务限流保留默认值；请求通过 HAProxy，未包含前端 BFF。
- Node 发压按计划到达率发送，延迟从计划发送时间开始计算；记录未发出的计划请求、传输失败及 HTTP 错误，不将发压端丢弃请求算成功。最大在途 512、HTTP socket 256。
- 混合请求：50% 热商品详情缓存，35% 搜索/筛选/分页，10% 私有查询，3% 购物车写，1% 报价，1% 下单。读路径等比例选择搜索/筛选/分页。报价与下单存在依赖。
- 缓存集中访问 100 个商品；混合场景每 100 个请求使用一个用户，不能视作 1,000 个同时活跃用户。混合 HTTP 场景不包含客户端付款动作。
- 各档顺序运行，共享种子数据和缓存，后台状态会累积；并非每档重置后的随机重复实验。

## 测量结果

成功 RPS 为成功响应数除以包含排空时间的实际运行时长。p95 包含失败请求；丢弃请求不进入延迟分位数。

| 场景 | 目标 RPS | 时长 | 成功 RPS | p95 | 失败 / 未发出 |
|---|---:|---:|---:|---:|---|
| 副本查询 | 400 | 120s | 399.9 | 67.7ms | 4 次连接重置 / 0，计划 48,000 次 |
| 副本查询 | 450 | 120s | 449.9 | 647.4ms | 0 / 0，延迟不达标 |
| 副本查询 | 500 | 45s | 483.3 | 1156.9ms | 0 / 300 |
| 副本查询 | 800 | 30s | 490.8 | 1333.7ms | 0 / 8,784 |
| 混合 HTTP | 400 | 30s | 399.2 | 25.8ms | 0 / 0 |
| 混合 HTTP | 500 | 120s | 499.7 | 50.7ms | 0 / 0，60,000 次全部成功 |
| 混合 HTTP | 800 | 30s | 641.3 | 1185.8ms | 8 次报价依赖失败 / 4,171 |
| 热详情缓存 | 1,000 | 30s | 999.2 | 9.2ms | 0 / 0 |
| 热详情缓存 | 2,000 | 30s | 1865.1 | 291.8ms | 3,450 次 503 / 397 |

500 RPS 混合档创建 600 单，约 5 单/秒；私有查询 p95 80.7ms，下单 p95 164.5ms。该档入口限流出现 `unavailable_open`：采样窗口入口约 0.87 次/秒、用户读约 0.067 次/秒，说明 HTTP 成功包含限流依赖不可用后放行，不能认定依赖完全健康。

## 对照与瓶颈

1. **API 进程是优先扩容点。** 800 RPS 副本查询时，两个进程各接近一个 CPU 核，两个副本各约 40% CPU。临时改为每容器 2 个进程后，同样 800 RPS 的成功吞吐升到 774.7 RPS，p95 834.2ms，仍丢弃 665 次计划请求。进程数翻倍也增加了总连接池容量，因此不能将收益全部归因于 CPU；依旧未达到延迟门槛。多进程下现有进程内 Prometheus 指标不能直接作为所有 worker 的聚合值。
2. **读写分离卸载主库，但有额外成本。** 副本读取时主库 CPU 接近空闲；临时切回主库读取，500 RPS 档成功 498.0 RPS、p95 193.1ms，主库 CPU 约 77%。这一轮主库直接读取更快。副本路径增加只读事务等交互，观察到副本档约 5 次 SQL/请求、主库档约 3 次；需要进一步逐段 profiling，不能仅凭一次顺序对照证明因果或给出固定提升倍数。
3. **饱和后等待显著放大。** 副本 800 RPS 档平均连接获取时间约 183ms，SQL 平均约 2.3ms；混合 800 RPS 档分别约 221ms、4.0ms。这些是采样窗口均值，获取连接指标不只代表排队，也会受建连/预检影响。增加数据库连接不能替代 API CPU 和请求成本优化。
4. **Redis 客户端预算需要一起处理。** 临时将每进程 Redis 连接上限由 10 调到 50，500 RPS 混合档采样未再见限流降级，但出现 14 次 `CATALOG_BUSY`，成功 499.2 RPS、p95 47.4ms。结果支持继续调查客户端池/超时，而非宣布 Redis 服务端已达到吞吐上限；单次实验不能证明已修复。
5. **支付后台尚未验收。** 混合阶段存在支付 `retry_wait`/`pending`，最终数据库快照仍有 285 个 retry_wait、14 个 pending、1 个 running。不同 API 暴露的是同一数据库计数，不能相加。未证明完整支付任务稳定排空，也未完成资金/库存核对。不要把 5 单/秒创建速度当作成功支付吞吐。
6. **规模与热点尚未覆盖。** 单次搜索 EXPLAIN 在 10k 数据上约 0.8ms，仍有标题过滤扫描；这不能证明百万商品搜索的能力。本轮未做热点 SKU 锁竞争、百万历史订单、跨主机网络、故障期间容量与 30 分钟/2 小时持续验收。

## 发压工具修正与无效样本

原有 `scripts/load_backend.py` 会读取系统代理，早期 `mixed-default-*` 出现代理 502；这些样本不用于容量判断。加入 `trust_env=False` 后重跑，`mixed-direct-10` 约 247 HTTP RPS、p95 28.2ms；20 条业务路径/秒时出现 429 和秒级等待。这种业务路径含轮询，不能与固定 HTTP 配比直接比较。

静态检查 `sh scripts/check.sh` 通过；现有 `tests/test_load.py` 3 项通过，没有增加或修改测试。

## 建议顺序

先联合调整 API 进程、网关并发、数据库/Redis 总连接预算，并测请求 CPU 与只读事务交互成本；随后定位支付任务重试与排空问题，再做独立发压机、真实 BFF 和更大数据集的持续测试。正式配置需以复测结果决定，本轮进程数和 Redis 池变更仅用于临时压测环境。
