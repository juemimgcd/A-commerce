# 全站 50,000 RPS 容量目标

2026-10-27 用户确认：目标为每秒 50,000 个全站混合 HTTP 请求，部署资源尚未确定。该目标取代原来的 1 万在线用户目标。当前状态是缓存改造与容量规划，尚未达到或验证 50,000 RPS。

## 固定验收口径

| 客户请求 | 占比 | 目标每秒请求数 |
|---|---:|---:|
| 商品浏览：列表、详情、搜索、筛选 | 85% | 42,500 |
| 私有查询：购物车、地址、订单/支付状态 | 10% | 5,000 |
| 普通写入：购物车、报价等 | 4% | 2,000 |
| 下单尝试 | 1% | 500 |
| 合计 | 100% | 50,000 |

统计点是实际应用入口，静态资源、健康检查、支付提供方回调和后台任务单列。通过前端 BFF 进入的流量必须包含 BFF 的开销，不以直连 API 的成绩替代。请求比例之外，商品浏览内部的列表/详情/搜索占比、热门商品分布、返回体大小、付款率、轮询频率仍需固定。下单尝试不等于成功订单 TPS。

按原 SLO 验收：目录 p95≤200ms/p99≤500ms，私有查询 p95≤400ms/p99≤1s，下单 p95≤800ms/p99≤2s；超时、5xx 和容量拒绝的 429 合计≤0.1%。正确性门槛仍为超卖、重复扣款/退款、重复订单、永久丢失已受理操作均为 0。后台积压不能持续增长。

## 当前实现与差距

| 位置 | 当前事实 | 下一步依据 |
|---|---|---|
| 商品缓存 | 列表首页和详情采用逻辑过期、后台刷新、跨实例租约与回源预算 | 分别测新鲜、旧值、冷启动、整体失效、Redis 故障 |
| 搜索/筛选/游标分页 | 使用独立短期查询缓存；配置读写分离后，回源走副本池，分类字典仍走主库 | 固定流量占比，测副本 SQL/索引、复制延迟、缓存命中和独立池等待 |
| 私有查询 | 数据库会话校验及业务查询 | 5,000 RPS 不能靠公共缓存消化，测鉴权与查询事务成本 |
| 下单保护 | 默认全局 20 次/秒，单 SKU 5 次/秒 | 必须在隔离环境证明下游能力后，设置匹配 500 次/秒的全局/用户/SKU/支付预算 |
| API 入口 | 两个普通 API，每进程 Uvicorn 并发上限 100，网关每后端 maxconn 80、队列 40；网关 maxconn 1024 | 实测单实例稳定吞吐，按 N+1 故障余量扩容，统一连接预算 |
| 入口 IP 限流 | 公共流量每 IP 10 秒 300 次 | 单台压测机先被限流；验收需真实多源地址或隔离压测入口，不能伪造转发头绕过信任链 |
| 数据库 | HA 普通 API 的商品搜索、筛选和分页可分流至副本；交易读写仍走主库 | 分别测量主从连接预算、慢 SQL、热点锁和 WAL/I/O；分流不等于容量达标 |
| Redis | cache/rate 两组独立主库，副本用于可用性；目录版本与快照原子读取，本地响应命中仍确认版本 | 按实际命令和 Lua 开销测量；不能把三副本吞吐当三倍主库吞吐 |
| worker/提供方 | 有界消费者与模拟支付提供方 | 量化每单任务数、服务时间、回调与重试，模拟器不能先成为压测瓶颈 |
| 现有压测工具 | 固定用户或业务路径到达率；浏览主要为详情和游标分页；仅允许本机地址 | 路径/秒不等于请求/秒，不能用该参数直接宣布 50k RPS；独立分布式发压方案待资源确定 |

本次不把现有开发部署的保护阈值直接改成 50,000，也不预先启用未验证的生产扩容配置。

## 用实测数据计算资源

- API：设单实例在目标比例、目标 SLO 和 CPU 余量下稳定处理 q RPS，则至少需要 `ceil(50000 / q)` 个可用实例，另加故障与发布余量。q 必须实测，不能引用纯框架 hello-world 成绩。
- 在途请求：50,000 RPS × 平均响应 20ms ≈ 1,000 个；平均 100ms 时约 5,000 个。该值用于连接/队列预算，不是建议直接设置的并发参数。
- 数据库：即使所有商品浏览完全命中，仍有约 7,500 次/秒私有或写请求，以及后台事务和目录回源。每请求可能多次数据库访问。逐类测量连接持有时间后计算总池，计入发布重叠与维护保留。
- 缓存：42,500 次浏览的 Redis 成本取决于响应缓存命中、版本读取合并、Lua 内部命令、限流和刷新，不能按每请求两次 GET 简单换算。按实际命令速率和延迟验收，未缓存路径必须单列。
- 网络：若平均响应体 10KiB，仅响应净载荷约 488MiB/s（4.1Gb/s），尚未计协议、复制、客户端请求和服务间流量。必须测实际响应体及链路余量。
- 后台：500 次下单尝试/秒按成功率、支付率和每单任务数换算任务到达率；消费者数量取决于实际任务服务时间与并发预算。保留回调/退款/恢复资源。

硬件清单至少包括 API/BFF、网关、PostgreSQL 主从、Redis 两组、RabbitMQ、worker、模拟提供方与压测机的 CPU、内存、磁盘、网卡、实例数和故障域。资源确定后才能产出可信的部署配额。

## 分阶段交付与验收

1. 完成目录逻辑过期与详情缓存，并运行现有后端回归。独立验证过期刷新与多实例竞争仍是待补专项，不能用普通回归替代。
2. 在确定的隔离环境测单 API、私有查询、下单和 worker 的稳定上限；保存代码/镜像版本、数据规模和监控。
3. 按瓶颈扩容或优化。优先处理未缓存的浏览路径、数据库查询与连接总预算、BFF/网关容量；仅在证据需要时引入搜索服务、读副本或分片。
4. 用独立压测节点按 5k / 10k / 20k / 35k / 50k RPS 逐级开放到达率。每级保存计划发送、实际发送、完成、丢弃、失败和延迟分位数，防止后端变慢导致发送率下降而虚假达标。
5. 在实际达到 50k 混合 RPS 后稳定 30 分钟，再进行 2 小时持续运行。数据至少包含 1 万 SKU、100 万历史订单和足够独立用户，按目标期间下单量准备库存及业务数据；正常阶段不能靠缺货拒绝降低事务成本。
6. 独立执行缓存整体失效、热点 SKU、依赖故障、滚动发布、主从切换与恢复；停止发压后核对资金/库存/订单并测积压排空时间。

正式报告必须给出每路由实际 RPS、成功订单 TPS、p50/p95/p99、429/5xx/超时、缓存状态、SQL/池/锁等待、API/Redis/数据库 CPU 与网络、队列最老年龄及业务核对。未固定资源并完成这些步骤之前，只能称为“50,000 RPS 目标”，不能称为“支持 5 万并发”。
