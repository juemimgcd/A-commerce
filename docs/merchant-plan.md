# A-commerce 商家角色与数据库建设大纲

> 文档版本：v1.0（最终纲要）\
> 定稿日期：2026-10-30\
> 适用范围：商家业务基础建设首版\
> 文档性质：确定本期业务范围、数据边界和验收规则，作为后续设计与开发依据。\
> 核对基线：本地 `/Users/jquery/python_files/A-commerce` 的账号、交易、库存、售后、报表和客服记忆实现；工作区包含未提交改动。本文不代表功能已实现、迁移已执行或生产验收已通过。

## 1. 阶段目标与范围

建立店主身份、店铺归属、商品管理、订单履约、售后和经营查询的完整基础。商家通过自己的用户账号管理获授权店铺；经营 Agent 复用相同业务服务，只读取本店数据并解释结果。

### 1.1 首版决策

| 事项 | 本期确定方案 |
| --- | --- |
| 商家账号 | 复用 `users` 和现有用户会话，同一账号可以购物和经营 |
| 平台管理 | 保留独立的 `staff` 及平台权限体系，不把店主变成平台员工 |
| 店铺数量 | 一个用户允许拥有多家店铺，每家店铺只有一名店主；本期不支持转让店铺 |
| 店铺人员 | 只有店主，不引入 `shop_members` |
| 开店方式 | 平台为已有用户创建店铺并启用；不建设自助申请、资质审核流程 |
| 订单边界 | 一份报价、一张订单、一个支付意图均只属于一家店铺 |
| 购物车 | 可以放入多店商品，按店分组，分别报价、下单和支付 |
| 商品与库存 | 复用 `products`、`skus`、`stock_items` 和库存流水 |
| 金额 | 人民币整数分，沿用现有整数金额类型；不使用浮点数表示金额 |
| 成本 | SKU 当前单位成本可为空；订单创建时固定单位成本快照 |
| 统计时间 | 持久化时间使用带时区时间；商家经营日按 `Asia/Shanghai` 划分 |
| 商家 Agent | 只读工具，不修改商品、价格、库存、订单、退款或用户设置 |
| 历史业务 | 归入独立的历史自营店铺；历史成本和无法证明的交易信息保持未知 |

### 1.2 本期交付

- 店铺管理、店主授权和店铺状态控制。
- 本店商品、SKU、售价、成本、图片、库存及上下架管理。
- 单店报价、下单、支付和订单归属。
- 本店订单查询、发货、售后审核、退货验收及既定流程内的退款。
- 销售、退款、库存、商品销量、成本覆盖和基础客户统计。
- 可追溯的商品毛利查询。
- 只读商家 Agent 工具及其授权、会话和返回字段隔离。
- 历史数据迁移、并发与重复请求边界、业务验收。

### 1.3 后续扩展

店铺员工、跨店合并支付与拆单、店铺转让、自助入驻、复杂营销、竞品分析、预测补货、跨店用户画像、共享客服记忆和 Agent 写操作不在本期。

本期“支付”指买家向现有支付链路付款，不新增向商家分账、结算、提现、佣金或税务核算能力。界面和 Agent 不得把销售额、净收款或商品毛利称为商家可提现余额。

现有平台功能继续保留。本期不自动向商家开放平台促销配置、对账处理、全局导出和用户管理权限；现有促销参与购买时必须遵守店铺与交易快照规则。

## 2. 用户、商家与店铺角色设计

### 2.1 身份与店铺授权

商家能力来自有效用户与 `shops.owner_user_id` 的关系，不新增独立商家密码或登录体系。用户会话只能证明账号身份，不能单独证明店铺权限。

用户进入商家功能后选择当前店铺。每个请求都携带明确的店铺目标，后端验证店主关系、账号状态、会话状态和操作权限，再访问资源。客户端传入的 `shop_id` 不构成授权。

平台员工继续通过独立会话和明确功能权限操作。平台操作与店主操作分别记录操作者类型、操作者标识、店铺、资源、动作和原因。

### 2.2 店铺模型与状态

新增 `shops`，至少包含：店铺标识、店主用户、名称、状态、退货地址、版本号、创建及更新时间。`owner_user_id` 建普通索引，不增加一人一店唯一约束。

| 状态 | 新交易与商品操作 | 存量订单与查询 |
| --- | --- | --- |
| `active` 营业中 | 允许上架、报价和新下单；允许店主维护商品与库存 | 允许履约、售后和经营查询 |
| `suspended` 暂停经营 | 停止新报价和新下单；买家侧不可购买；店主可下架和补充履约资料，不可新增或上架商品、改价、直接调库存 | 允许有效店主处理既有订单、退货和查询；平台可以介入 |
| `closed` 已关闭 | 不允许新交易或店主业务写入 | 店主只读历史数据；遗留问题由有权限的平台员工处理 |

店铺状态由平台管理。关闭前必须检查未结束订单、退款、退货和异步任务；存在未完成事项时拒绝正常关闭，先暂停经营并完成处理。本期不提供已关闭店铺重新营业功能。

暂停经营使尚未下单的报价不可再提交，但不直接抹除既有订单；既有待支付订单继续走原支付、超时关闭和库存释放流程。账号禁用会阻止该账号全部商家访问，未完成履约由平台接管。

### 2.3 操作权限

| 操作 | 买家 | 店主 | 平台员工 |
| --- | --- | --- | --- |
| 创建、暂停、恢复、关闭店铺 | 无 | 无 | 具有店铺管理权限时允许 |
| 修改店名、退货地址 | 无 | 本店，按状态允许 | 具有店铺管理权限时允许 |
| 商品、SKU、成本、图片、库存管理 | 无 | 本店，按状态允许 | 具有相应商品或库存权限时允许 |
| 查询订单 | 自己购买的订单 | 本店订单 | 具有相应订单权限时允许 |
| 付款、买家取消、申请退货 | 本人订单，遵守原状态机 | 以买家身份操作自己的购买订单 | 不通过商家入口代替买家支付 |
| 发货、售后审核、收件、验收 | 无 | 本店订单，遵守原状态机 | 具有履约或售后权限时允许 |
| 退款 | 通过既有取消或售后流程触发 | 通过本店已授权售后流程触发，不任意输入退款金额 | 保留现有授权流程，额外操作需原因及审计 |
| 经营统计与成本查看 | 无 | 本店 | 具有报表权限时允许 |
| 全局用户、记忆洞察、平台对账 | 无 | 无 | 保留现有独立权限 |

金额变更、库存调整、履约和售后写入均在事务内再次核验授权和资源归属。平台原有敏感操作的近期登录要求继续保留；店主发货、售后审核及验收采用最近 15 分钟内登录的要求。

## 3. 核心数据模型与归属

### 3.1 现有实现映射与调整

| 现有模型或表 | 本期处理 |
| --- | --- |
| `users`、`staff`、`sessions` | 复用；增加店铺授权服务，不混用用户与平台员工权限 |
| `shops` | 新增店主、状态、退货地址和版本信息 |
| `products` | 增加 `shop_id`；商品归属在创建后不可由商家修改 |
| `skus` | 复用规格、售价与版本；增加可空的当前单位成本；保留现有 SKU 编码唯一规则 |
| `stock_items`、`stock_movements` | 复用实物、预留、已分配库存及流水，不在 SKU 上重复保存库存 |
| `quotes` | 增加店铺归属、店铺规则版本和本次定价信息；公开报价不得泄露成本 |
| `orders` | 增加不可变的成交店铺归属；复用金额、支付时间、地址和规则快照 |
| `order_items` | 复用商品名称、规格、数量与成交单价；补充商品、品类、原价、优惠及成本快照 |
| `payment_intents` | 保留与订单的一对一关系 |
| `refunds`、`return_requests`、`return_items` | 复用；补充退款金额分配及退货验收结果，确保金额、数量和原成交明细可追溯 |
| `shipments` | 复用首版一单一发货记录及原物流状态机 |
| `financial_entries` | 复用支付、退款入账事实及唯一业务引用，通过订单关联店铺 |
| `daily_reports`、`product_daily_reports` | 保留平台用途；商家首版使用带店铺过滤的交易事实查询，不直接返回平台聚合结果 |
| `product_media` 等管理记录 | 将原来仅记录平台员工的写入路径扩展为可记录店主或员工，并验证所属商品的店铺 |
| 客服记忆与共享设置 | 保留现有平台用途，本期不改造成商家数据来源 |

这里规定的是数据职责与约束。新增字段和辅助表的最终名称可以遵循仓库约定，但不得改变本纲要的业务语义。

### 3.2 数据归属与不可变性

- 商品属于店铺；SKU、库存和图片通过商品确定归属。
- 报价与订单分别记录店铺，订单中的买家仍由 `user_id` 标识。
- 同一订单的全部明细必须属于同一店铺，下单时在事务内校验。
- 发货、退款、退货和经营统计通过成交订单确定店铺，不从商品当前属性推测历史归属。
- 本期不提供商品跨店转移或店铺转让。确需在另一店经营时创建新商品，历史交易归属不变。
- 品类变更不能改写历史品类统计，因此新订单保存成交时的品类标识与名称快照。
- 已参与交易的商品、SKU、店铺和订单不得硬删除；通过下架或状态控制保留历史关联。
- 买家输出、商家输出、平台输出和 Agent 输出分别定义字段白名单，避免新增成本字段后通过通用序列化泄露。

### 3.3 约束、索引与查询边界

新增关系建立外键；金额、数量、成本、退款分配和库存余额建立适用的检查与唯一约束。成本可为空，非空时必须大于等于零；零成本表示已明确记录为零，不能用来代替未知。

核心查询支持店铺加时间、状态、资源标识的组合访问。索引至少覆盖商品按店铺查询、订单按店铺与创建时间分页、订单按店铺与支付时间统计、退款按订单与完成时间查询。分页使用稳定排序，列表最多返回 100 条，统计区间最长 366 天。

权限、店铺状态、交易确认和经营统计读取主库。现有公开商品读副本、缓存、搜索索引和商品快照需要纳入店铺状态更新与失效流程；即使公开列表短暂延迟，报价和下单仍必须按主库状态拒绝新交易。

## 4. 订单、履约与库存设计

### 4.1 单店结算

购物车按店铺分组，买家对每家店独立确认报价、运费和支付。一次请求含多店商品时，后端返回明确的跨店结算错误，不静默拆单、不部分创建订单、不部分扣库存。

运费按每张店铺订单计算。首版复用平台现有运费规则，不新增商家自定义运费引擎；买家需能看到各店分别收取的运费。

一张订单下单失败不会创建半张订单；不同店铺独立结算的成功与失败相互独立。重复提交同一报价或幂等键继续返回原结果，不重复创建支付或占用库存。

### 4.2 交易写入

沿用现有报价校验、版本检查、库存锁、事务、Outbox 和异步恢复链路。下单事务同时完成：

1. 校验会话、店铺营业状态、报价归属和有效期。
2. 校验全部商品归属、可售状态、价格及规则版本。
3. 固定成交明细、成本、地址、退货地址和售后规则快照。
4. 预留库存，创建订单、明细和支付意图。
5. 写入幂等结果、库存流水、审计与待发送事件。

成本变更不改变已创建订单；成本单独更新不应使买家因隐藏的经营字段变化而重新报价。成本读取与订单创建必须通过同一锁定协议获得一致快照。

暂停店铺与下单使用一致的事务锁定规则：暂停提交后开始的新下单不得成功；已经提交的订单按存量订单处理。

### 4.3 库存管理

继续采用：可售库存 = 实物库存 `on_hand` − 预留库存 `reserved` − 已分配库存 `allocated`。

店主执行入库或盘点调整时提交变动数量、原因和幂等键；通过库存服务加锁、校验并写入流水。禁止直接覆盖预留或已分配库存，调整后的实物库存不得小于二者之和。

下单预留、支付分配、取消释放、发货扣减、可再售退货入库复用既有状态迁移。退货验收入库属于存量售后处理，在暂停经营期间仍允许执行。

### 4.4 售后与退款

复用现有售后期限、申请、批准、寄回、收件、验收和退款流程，不增加商家任意赔付能力。新订单固定本店退货地址和适用规则；修改店铺当前退货地址不改写既有订单。

退款必须区分商品金额与运费金额，并记录分配到原订单明细的商品退款额。各明细累计成功及处理中退款不得超过该明细实付金额，整单累计退款不得超过实付总额。

未发货整单取消按原流程退全额；发货后的退货按原成交明细实付金额退款，不退运费，包括分次退回全部商品的情况。新增优惠分摊后，退款使用分摊后的实付金额，不使用商品当前价格。

记录验收时间、退回数量、是否可再售及实际入库流水。首版沿用一次退货验收整体判定可再售与否的方式，不增加逐件分级质检。申请中的退货占用数量不得被当作已验收入库数量。

支付、退款和物流状态沿用既有业务状态机及失败恢复机制。异步任务内部必须校验资源关联，不能因为无需前台会话就跳过订单与店铺的一致性检查。

## 5. 交易快照、金额与统计口径

### 5.1 成交快照与金额等式

新订单明细至少保存：SKU、商品与品类引用及展示快照、数量、优惠前单价、成交单价、明细优惠额、明细实付额和可空的单位成本。

- 明细优惠前金额 = 优惠前单价 × 数量。
- 明细实付额 = 明细优惠前金额 − 明细优惠额。
- 订单实付总额 = 各明细实付额之和 + 运费。
- 当前秒杀等直接改价产生的价差记录为本次明细优惠，不能再次从实付额中扣除。
- 本期不新增订单级优惠券和复杂促销分摊。以后增加时，必须先定义整数分舍入及尾差归属规则。

成本在订单创建时读取并固定。首版将其定义为“商家录入的单位商品成本”，不引入批次成本、加权平均成本、运费分摊、平台手续费和会计核算。

### 5.2 两类报表分别展示

为避免跨月退款混用口径，商家界面和 Agent 必须区分以下两类查询，不能把它们直接相减拼成利润。

| 报表 | 时间与计算规则 |
| --- | --- |
| 期间收款与退款 | 支付按 `paid_at`，退款按 `confirmed_at` 计入发生期间；分别展示商品收款、运费收款、商品退款、运费退款和净收款 |
| 成交订单经营表现 | 选择支付时间落在区间内的订单，再计算这些订单截至查询时点的退款、退货、销量与商品毛利；返回统一的“截至时间” |

例如 10 月支付、11 月退款：10 月收款记录不变，11 月退款增加；查询“10 月成交订单截至 11 月某日的表现”时，该笔退款会减少这批订单的净商品收入。

时间区间统一使用左闭右开 `[start, end)`。日期查询按上海时区日界线转换成数据库时间。单次报表使用同一数据库一致性快照及同一个截至时点，避免收入与退款来自不同读取时刻。

首版截至时点由服务端取本次查询的快照时间，不支持用户任意指定过去时点重建历史报表。对比后台与 Agent 结果时使用同一份查询结果或同一固定数据快照。

### 5.3 销量、成本与商品毛利

成交订单经营表现使用以下规则：

- 支付销量：选定已支付订单的原成交数量。之后退款不抹除支付事实。
- 已验收退货量：截至时点实际验收完成的退货数量，单独展示。
- 商品净收入：原明细实付额减截至时点已成功的商品退款，不包含运费。
- 对已支付订单，初始商品成本为订单单位成本快照乘成交数量。
- 未发货取消且退款成功的商品，冲回对应商品成本；取消处理中或退款未成功时暂不冲回。
- 已发货商品仅在退货验收且实际可再售入库后冲回对应成本；报损或仅退款不冲回成本。
- 同一单位商品不能同时因取消和退货重复冲回成本。
- 商品毛利 = 商品净收入 − 未冲回的商品成本。它是本项目的经营测算值，不是净利润或正式会计利润。

退款成功和可再售入库可以先后发生，因此中间时点的毛利会变化。结果必须同时返回退款处理中金额、待处理退货状态和截至时间，不能把中间状态描述为最终结果。

### 5.4 未知成本与覆盖范围

只对单位成本已知、且所需退款和退货归属可追溯的明细计算商品毛利。未知明细不按零成本计算，也不纳入“已知成本部分”的收入分子。

成本覆盖率 = 所选支付订单中成本已知明细的原始实付商品金额 ÷ 全部明细的原始实付商品金额。分母使用退款前商品金额，避免退款使覆盖率失真；分母为零时返回“不适用”。

可计算毛利的明细覆盖率 = 成本已知且退款、退货归属完整的明细数 ÷ 所选支付订单的全部明细数，分母为零时返回“不适用”。同时返回这部分明细的净收入、成本及未覆盖原因。存在无法分配到明细的历史退款时，即使成本已知，也不能声称毛利完整。

### 5.5 统计示例

一件商品实付 100 元、成本快照 60 元、运费 10 元，已支付：期间收款为 110 元，商品毛利为 40 元。

- 未发货取消并成功退回 110 元：该订单商品净收入和成本均为零，商品毛利为零。
- 发货后退回商品、可再售入库且成功退商品款 100 元：商品净收入和成本均为零；运费仍单独保留，不计入商品毛利。
- 商品退款 100 元但退货报损：商品净收入为零、成本仍为 60 元，商品毛利为 −60 元。
- 成本未知：展示收款和退款，但毛利为未知，不展示为 100 元。

## 6. 客户洞察与数据使用边界

### 6.1 本期基础统计

以本店真实支付订单为依据，提供去重购买人数、新老客、支付次数、商品消费额、品类和收货地区分布。

- 购买人数：区间内在本店至少支付一次的用户数；退款不抹除曾购买事实。
- 新客：首次在本店支付的时间位于本区间；老客：本区间购买且首次支付早于区间起点。
- 同一用户在区间内重复购买仍只计一个新客或老客，按用户分类而不是按订单混合计数。
- 消费额分布使用所选支付订单截至查询时点的商品净收入，运费单列；不称为用户全平台消费额。
- 品类使用成交快照；历史缺少品类快照时归入“未知”，不从当前品类伪造历史。
- 地区使用订单收货地区快照；它代表收货地区，不推断为用户居住地。

不新增独立客户账号表。首版不建设客户标签、客户汇总表或专用统计调度任务；先从带店铺过滤的交易事实获得正确结果，后续按实际性能证据决定聚合方案。

### 6.2 信息可见范围

商家履约接口可以按本店订单返回必要的收件人、电话和地址，并记录敏感信息访问。经营统计默认返回聚合数据，不输出全量客户联系方式。

现有全局客服记忆、原始对话、候选偏好、功能使用记录及平台洞察不开放给商家。本期不复用全局 `share_with_merchant` 开关作为任意店铺的访问许可，不改变既有记忆、共享和营销设置。

未来共享偏好时，必须另行定义被授权店铺、允许字段、撤回效果和营销用途；本店发生过交易本身不授予读取跨店行为或客服对话的权限。

## 7. 商家接口与 Agent 接入

### 7.1 商家业务服务

提供店铺列表及当前店铺查询、商品与 SKU 管理、成本维护、图片管理、库存变动、订单列表及详情、履约、售后、期间收退款、成交订单经营表现和基础客户统计。

商家接口必须先获得经后端校验的店铺上下文，再执行资源查询。不能先返回全平台数据后由前端过滤。单资源访问同样使用店铺范围，越权请求采用统一的资源不可访问响应。

写操作沿用现有版本校验、幂等处理和审计。版本冲突应明确返回，不能静默覆盖他人变更。查询支持稳定分页，统计返回币种、口径版本、时间区间、截至时间及数据覆盖情况。

### 7.2 Agent 工具范围

| 工具能力 | 允许输入 | 返回内容 |
| --- | --- | --- |
| 查询期间收退款 | 起止时间 | 本店收款、退款、净收款及口径 |
| 查询成交订单经营表现 | 起止时间、可选商品 | 本店销量、商品净收入、成本覆盖和商品毛利 |
| 查询订单列表 | 状态、分页条件 | 本店订单的脱敏摘要 |
| 查询商品与库存 | 商品、分页条件 | 本店价格、成本及库存状态 |
| 查询客户统计 | 起止时间 | 本店聚合购买统计 |

工具名称按现有工具规范实现；表中能力范围是固定边界。Agent 不获取直接 SQL 执行能力，也不接受模型生成的用户标识、店主标识作为授权依据。

### 7.3 会话、工具和输出隔离

- 用户在商家界面选择店铺后，后端将已校验的店铺绑定到商家会话和运行上下文。
- 一次运行只绑定一家店铺；切换店铺创建独立商家会话，不沿用另一店铺的上下文、工具结果或缓存。
- 买家客服会话与商家经营会话分开；商家成本不能进入买家客服上下文。
- 每次工具调用重新检查会话、账号、店铺归属及状态，不能只在创建会话时授权一次。
- 工具读取与普通商家接口复用授权和计算服务，缓存键必须包含店铺与口径，禁止复用全平台缓存。
- Agent 订单摘要排除姓名、电话、完整地址、支付凭据和全局用户标识；需要履约详情时提供指向本店后台的链接，由后台重新授权。
- 数值由业务服务计算，Agent 只能解释；成本不足、查询失败或口径不适用时如实说明，不补造经营结果。
- 记录工具、店铺、调用人、查询范围及结果状态，不将敏感明文写入普通日志。

## 9. 验收标准

### 9.1 业务闭环

使用平台账号、店主 A、店主 B 和买家账号；为 A 创建两家店，为 B 创建一家店。

- [ ] 平台可创建和启用店铺，店主可切换自己的店铺。
- [ ] 店主可购物，也可管理自己的店铺，二者权限互不扩大。
- [ ] 各店商品可独立维护；购物车多店分组，各店分别下单和支付。
- [ ] 商家完成本店发货、售后审核、验收及规定退款。
- [ ] 本店销售、库存、退款、成本覆盖与毛利符合第 5 节公式和示例。

### 9.2 隔离与状态

- [ ] 修改店铺、商品、SKU、图片、订单、退货或退款标识均不能越权。
- [ ] 平台员工功能权限继续生效，普通店主无法调用平台全局接口。
- [ ] 公开接口、买家客服、商品缓存及搜索结果不暴露成本。
- [ ] 暂停后拒绝新报价和新下单；既有订单可继续支付、履约和售后。
- [ ] 有未完成事务的店铺不能直接关闭；禁用账号后，旧会话和 Agent 工具均不能继续访问。
- [ ] 切换店铺不会保留另一店铺的 Agent 上下文或工具结果。

### 9.3 交易一致性

- [ ] 混合店铺报价和订单被整体拒绝，没有部分库存或订单副作用。
- [ ] 重复下单、支付通知、退款确认和退货验收不重复占库存、记账或入库。
- [ ] 并发库存调整不能使实物库存低于预留与已分配之和。
- [ ] 退款预占和已退金额不得超出订单与明细可退余额。
- [ ] 退款成功、可再售入库和成本冲回分别有明确依据，不因重试重复应用。
- [ ] 商品改名、改价、改成本、改品类及店铺改地址，不改写既有订单快照。
- [ ] 原异步重试、支付关闭、对账与故障恢复链路未被商家扩展破坏。

### 9.4 统计与历史数据

- [ ] 待支付、支付失败和未支付关闭订单不计入支付销量或商品收入。
- [ ] 已支付后退款的订单保留原支付事实，并按两类报表各自口径反映退款。
- [ ] 跨月退款、上海时区午夜边界、未知成本、零成本、报损和仅退款结果正确。
- [ ] 新客与老客按本店首次支付定义，同一用户跨店身份不混算。
- [ ] 历史归属、资金总额、退款总额、库存余额与迁移前核对一致。
- [ ] 无法证明的历史成本、优惠、品类和退款分配标记未知，不伪造完整利润。
- [ ] Agent 与商家后台在相同店铺、口径和截至时点给出一致结果。

## 10. 历史数据迁移与发布规则

### 10.1 历史归属

当前没有商家归属的数据统一进入独立的“历史自营店铺”，不凭商品品牌、名称或买家身份猜测真实商家。该店铺只用于承接原平台自营业务，由专用用户账号作为店主，日常迁移与接管由授权平台员工执行。

所有既有商品及订单归入该店铺，连带维持原支付、发货、售后、流水与媒体关联。专用账号未完成激活时不提供店主登录，也不得因此开放匿名访问；完成账号配置和业务核对后再启用自营店的新交易。

若实施基线出现已经存在的真实商家归属，应保留其证据化映射，不覆盖到历史自营店铺；映射冲突阻止该批迁移上线，不以默认值消除冲突。

历史订单只回填能够从原快照、退款、退货和流水证明的事实。不得从当前 SKU 成本、当前标价或当前品类推断历史信息；不足部分标注未知。历史订单继续可查、可履约和售后，统计明确显示覆盖范围。

### 10.2 迁移顺序

1. 记录实际版本、数据量、资金与库存基线，准备备份和恢复步骤。
2. 以 Alembic 增量迁移新增店铺及暂可空的归属、快照和退款关联字段；不重建现有交易表。
3. 回填历史自营店铺及可证明的交易关联，按批次记录进度，迁移可重入。
4. 在最终切换窗口暂停新增交易及后台业务写入，使回调、worker 和迁移按既有重试机制协调；冻结最终回填的数据边界，避免旧写入产生无归属记录。
5. 核对外键、店铺归属、明细合计、退款余额、库存余额和原业务总量；修复异常后再增加必需的非空约束。
6. 旧报价统一失效，买家重新报价；已经创建的订单保留原支付意图、金额、库存和履约状态。
7. 切换全部相关 API、worker、定时任务与事件消费者，禁止新旧写入路径长期并行。更新公开目录缓存和搜索内容后恢复服务。
8. 以第 9 节场景进行发布核验，记录尚未覆盖的历史统计范围。

### 10.3 失败处理

上线前失败保持旧业务版本并修复迁移，不删除原数据。恢复交易后若出现问题，先停止新商家写入，保留支付回调和恢复处理能力，以修复或兼容版本恢复服务。

不得对已产生的新商家订单直接回滚表结构，也不得将数据库恢复到早期备份后忽略已发生的外部支付。需要数据恢复时，必须核对支付提供方事件并完成差异恢复，之后才能恢复交易。
