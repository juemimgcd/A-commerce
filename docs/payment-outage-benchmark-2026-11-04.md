# 下单后支付任务异步恢复验证（2026-11-04）

## N 与 T

两轮独立隔离环境中，支付模拟服务停机约 20 秒期间均成功创建 **N=100 笔订单**。从发起支付模拟服务重启，到提供方支付单全部存在且应用侧全部进入待支付状态，**T 分别为 6.108 秒、5.793 秒**。

| 指标 | 第一轮 | 第二轮 |
| --- | ---: | ---: |
| 计划下单数 / 独立用户数 | 100 / 100 | 100 / 100 |
| 目标下单速率 | 10 笔/秒 | 10 笔/秒 |
| 停机确认至发起重启 | 20.002 s | 20.008 s |
| 成功创建订单 N | 100 | 100 |
| 下单 HTTP P95 | 94.226 ms | 99.577 ms |
| 中断期间 Outbox 未投递采样峰值 | 10 | 11 |
| 中断期间 RabbitMQ ready 采样峰值 | 98 | 98 |
| 中断期间 RabbitMQ unacked 采样峰值 | 1 | 1 |
| 重启命令至就绪 | 0.644 s | 0.626 s |
| 重启命令至全部支付单创建并本地确认 T | 6.108 s | 5.793 s |
| 提供方就绪至上述完成条件 | 5.463 s | 5.167 s |
| 最终提供方支付单 / 本地支付意图 | 100 / 100 | 100 / 100 |
| 最终库存预留 / 已分配 | 100 / 0 | 100 / 0 |

两轮下单请求全部返回 201，无 429、5xx 或传输错误；默认流量配额保持不变。每轮 100 个订单 ID、支付意图 ID 和提供方支付单一一对应，金额及商户标识一致，未观察到额外支付单。

**支付单创建不等于付款成功**：本次不调用模拟付款接口，所有订单未付款、库存仍为预留。支付任务此时保持 `retry_wait`，以继续定期查询付款状态；不能将本次结果描述为“全部订单支付成功”或“全部支付任务 done”。

## 场景与流程

1. 使用 100 个独立测试用户、10 个商品，每商品库存 1,000；经真实 HTTP 报价接口预先取得 100 个报价。
2. 支付模拟服务最初正常运行，验证鉴权 `/ledger` 可访问，然后停止该进程；确认连接失败后才开始计停机时间。
3. 服务中断期间，以 10 笔/秒提交 100 次真实 `POST /api/v1/customer/orders` 请求，每个用户提交一次、使用独立幂等键。订单、库存预留和支付任务 Outbox 按应用原有事务提交。
4. relay 与 critical worker 全程运行。RabbitMQ 接收支付任务；支付调用失败由现有逻辑记录 unknown、安排退避重试。没有暂停消费者、没有人工增加业务处理延迟、没有直接插入订单或支付单。
5. 停机约 20 秒后启动同一支付模拟服务，复用原 SQLite 文件及配置。记录重启发起时刻、首次成功鉴权响应时刻，以及双端完成条件首次满足的时刻。
6. 对照成功下单响应、本地订单/支付意图和提供方真实 SQLite 支付记录，核验 ID、金额、商户、状态、库存；证据保存后清理本轮进程和 Docker 项目。

该场景验证“支付服务暂不可用时，下单事务可以先完成，支付创建任务通过 RabbitMQ 和持久化重试状态恢复”。不能说明 RabbitMQ 让同步订单写入避开数据库，也不是异步下单或下单入口削峰测试。

## 环境与测量边界

- macOS Apple Silicon，本机真实 TCP HTTP，Python/HTTPX 发压；不是 JMeter，也不是线上用户流量。
- 一次性 Docker PostgreSQL 18.6（2 CPU / 1 GiB）、RabbitMQ 4.4.0（2 CPU / 1 GiB）、Redis 7.4.9（1 CPU / 256 MiB）。RabbitMQ 单节点 quorum 队列，未验证多节点容错。
- API、relay、critical worker、支付模拟服务各 1 个进程，均使用当前项目实现；独立 `commerce_payment_test` 数据库/vhost、随机 loopback 端口及临时凭证。
- 保留默认入口、用户、下单全局和 SKU 限流，以及默认 worker 并发、预取、HTTP 超时和任务重试配置。每商品平均 1 次下单/秒、每用户只下单一次；没有提高配额来获得 N。
- N 是这 100 次计划请求中实际创建成功的订单数量，不代表系统在停机期间可无限接单。应用仍有默认 1,000 个关键积压任务的结算保护阈值，本次未触及。
- T 包含服务进程启动、当前任务超时/退避、扫描补发、队列等待、提供方创建及应用写回；主口径从重启发起计时，避免只报告较短的就绪后耗时。
- 完成条件为提供方支付单数等于 N 且应用侧 N 个订单的支付状态均为 pending；随后逐条核验 IDs/金额/商户。约 100 ms 采样，T 含观测轮询误差，不是精确到毫秒的生产 SLA。
- RabbitMQ 管理 API 约 1 秒读取一次，broker 统计可能滞后。表中队列峰值是中断窗口内的采样值，不是严格瞬时上界；最终统计可能仍显示旧的 ready/ack 数，不能据此声称队列已排空。**T 是支付单创建恢复时间，不是 RabbitMQ 队列排空时间。** 后续待支付查询任务仍会继续产生。
- 下单 HTTP 延迟从实际发起请求到响应读取和 JSON 解析完成；调度迟延另存，P95 分别为 3.022 ms、4.671 ms。未剔除慢请求、未对失败请求自动重发。
- 没有真实扣款、没有生产支付网关、没有同步调用对照组。不能把这两个短时本地故障演练写成生产可用性或吞吐容量证明。

## 复现与证据

```sh
PYTHONPATH=src .venv/bin/python scripts/benchmarks/payment_outage.py
```

脚本自动创建隔离服务、迁移、构造测试账号和商品、准备报价、停机、下单、恢复、核验并清理。不会连接业务数据库或发出真实支付请求。

- [可复用脚本](../scripts/benchmarks/payment_outage.py)
- 第一轮：`var/validation/commerce-payment-outage-20261104t051718z-ce36/`
- 第二轮：`var/validation/commerce-payment-outage-20261104t051841z-94e4/`
- `summary.json`：N/T、默认配额、HTTP 延迟、故障前后状态及逐项校验结论。
- `orders.json`：全部下单请求的状态、响应、延迟与调度迟延。
- `snapshots.jsonl`：订单状态、Outbox、重试任务、提供方支付单数量时间序列。
- `broker-stats.json`：RabbitMQ ready/unacked 及投递计数采样。
- `payment-sessions.json`、`provider.sqlite3`：本地订单/意图及提供方持久化事实。
- API、relay、worker、提供方与 Docker 服务日志保留在各自目录；原始证据目录不纳入 Git。
