# 商品浏览三层对照与优化记录

日期：2026-10-30。目标为公开商品 API 10,000 RPS，不包含下单吞吐、网页 SSR、图片、TLS 或 CDN。

本文保留第一轮实测时的代码与迁移状态。后续优化及 30 分钟最终结果见 [第二轮记录](catalog-benchmark-round2-2026-10-30.md)，当前工具与主线验证见 [商品浏览优化与压测工具](catalog-performance.md)。下文迁移回归失败是历史记录，已由后续主线修复，不表示当前回归仍失败。

**10k 尚未通过。** 最终版本的 120 秒容器网络测试完成约 9,873 RPS，实际发出的 1,184,982 个请求全部成功，但有 15,018 个计划请求未发出；整体 p95 211ms，分页 p95 237ms。不能将“实际请求零错误”解释为已经承接全部 10,000 RPS。

## 环境与口径

- MacBookPro18,4，10 核、32 GiB；Docker 分配 10 CPU、约 7.75 GiB。
- 一次性项目 `commerce-catalog-20261030t052150z-05e1`，单 PostgreSQL 主库，缓存与限流各有一组 Redis Sentinel，保留网关、worker、RabbitMQ 和监控。没有修改业务 `.env` 或连接现有业务数据库。
- 合成数据：10,000 商品、1,000 用户，无历史订单。不能据此推断真实商品复杂度、生产搜索分布或历史订单容量。
- HTTP 经过 HAProxy 和真实 API。基线为 2 个 API 进程，扩容组为两个容器各 4 个进程。
- 浏览比例：50% 商品详情、20% 首页、10% 搜索、10% 价格筛选、10% 游标分页。按生成器实际索引，详情命中 50 个不同商品，搜索 10 个不同词，价格筛选 1 组，游标 1,000 个；这是有限工作集，不能称为任意长尾查询 10k。
- 固定到达率；高压使用 4 个 Node 发压进程。每个进程上限 512 个在途请求，最多 256 个 HTTP 连接；计划请求延迟超过 200ms 或在途已满时记为 `dropped`。不把未发出的请求、429、503 算作成功。
- 延迟从计划发送时间计到完整响应结束，包含发压调度滞后。JSON 保存计划、实际发送、成功、丢弃、状态码和各接口分位延迟；合并分位数使用毫秒直方图，不能将各进程 p95 简单平均。
- 因所有请求源自一个发压 IP，只在隔离环境放宽入口 IP 限额。应用仍逐请求执行共享令牌桶；交易和用户额度保持默认。该覆盖不是生产限流建议。

## 三层基线

| 层次 | 条件 | 实测成功吞吐 | 观察 |
|---|---|---:|---|
| Redis 原始 GET | 跨容器，32 连接，无 pipeline，508 B 商品缓存，200,000 次 | 125,628 ops/s | p95 0.215ms，p99 0.279ms |
| 应用 Redis 客户端 GET | 单 Python 进程，32 并发，池 50，15 秒 | 30,931 ops/s | CPU 约 99.6%，无错误 |
| 应用完整目录函数 | 单 Python 进程，32 并发，池 50，15 秒 | 13,080 ops/s | 包含版本读取、缓存 JSON/Pydantic 解析 |
| 完整 HTTP 热详情 | 2 API，输入 1,000 RPS，30 秒 | 998 RPS | 无失败/丢弃，p95 9.3ms |
| 完整 HTTP 热详情 | 2 API，输入 2,000 RPS，30 秒 | 1,668 RPS | 9,560 个计划请求未发出，p95 336.6ms |
| 完整 HTTP 浏览组合 | 2 API，输入 500 RPS，30 秒 | 500 RPS | 无失败/丢弃，p95 12.7ms |

这里的 GET ops/s 不能当作 HTTP RPS：载荷、限流、路由、序列化和日志成本不同。结论是基线先受应用链路限制，没有证据表明 Redis 服务端已达到上限。

池 10、并发 32 的客户端组在 15 秒内产生 322,028 次 `ConnectionError`；池 50 后错误消失，但成功吞吐没有数量级增长。连接池容量与单进程处理能力是两个不同限制。

## 已实现的改动

1. 资源依赖改为异步函数，省去每个请求只为读取内存对象而往返线程池的成本。
2. HTTP 日志、请求编号、指标和异常响应改用直接 ASGI 中间件；保留逐请求观测。高频目录路由前移。
3. 版本与缓存值合并为原子 Lua 读取，使用 `EVALSHA`；限流同样使用脚本摘要，仅 `NOSCRIPT` 允许重新发送脚本文本，未知结果的超时不重试扣减。
4. 搜索、分类、品牌、属性、价格、库存筛选和分页使用参数完整、来源隔离的查询缓存。默认 15–20 秒；不把副本数据填入主库详情快照。
   最后 3 秒可用同一租约和回源预算提前刷新，失败不延长原期限，避免周期性过期竞争。
5. 仅公开商品列表/详情复用已校验的 JSON 响应，默认 1 秒，可配置到 5 秒；最多 64 KiB/响应。进程内 LRU 最多 1,024 条、正文 8 MiB。每次仍读 Redis 当前目录版本、执行入口限流；Redis 不可用时不返回本地副本。
6. 响应复用继承底层绝对截止时间，访问不续期。回调专用 API、私有数据、错误和媒体不进入此缓存；报价、下单继续查数据库。
7. Redis 默认连接上限从 10 调到 50，池满最多等待 50ms。等待只吸收短时峰值，不是吞吐保证；限流仍有 350ms 总预算。

代码与缓存语义见 [catalog-cache.md](catalog-cache.md)。

## 网关与网络对照

初始网关每个 API 容器仅允许 80 个上游连接。高压日志样本中，后端排队平均约 118ms，API 内部约 12ms。只增加 API 进程仍被入口预算限制。

隔离环境最终覆盖：HAProxy `nbthread 2`、全局 `maxconn 4096`、每个普通 API 上游 `maxconn 256 maxqueue 128`；每个 API worker 的 Uvicorn 并发上限 256、Redis 池 100。8 个 worker 的主库连接上限合计 40、目录回源并发合计 32，两组 Redis 每组最多 800 条 API 客户端连接；另计回调、worker、监控及滚动重叠。这些覆盖没有写入默认部署文件。

| 版本/路径 | 时长 | 输入 | 成功 RPS | 未发出 | p95/p99 |
|---|---:|---:|---:|---:|---:|
| 响应缓存 + 联动预算，宿主机端口 | 90s | 10,000 | 7,861 | 184,102 | 365/481ms |
| 增加有界池等待，宿主机端口 | 90s | 10,000 | 7,202 | 249,596 | 427/534ms |
| 增加本地响应副本，宿主机端口 | 90s | 10,000 | 7,705 | 203,634 | 408/523ms |
| 同一版本，容器网络直接到网关 | 90s | 10,000 | 9,881 | 9,369 | 188/280ms |
| 响应窗口提高到 5 秒，容器网络 | 180s | 10,000 | 9,613 | 68,703 | 266/358ms |
| 最终版：1 秒响应 + 查询提前刷新，容器网络 | 120s | 10,000 | 9,873 | 15,018 | 211/290ms |
| 同一最终版，容器网络 | 120s | 8,000 | 7,989 | 1,173 | 97/224ms |
| 同一最终版，宿主机端口 | 120s | 5,000 | 4,996 | 0 | 58/127ms |
| 上游连接加到 512/容器，容器网络 | 120s | 10,000 | 8,777 | 143,393 | 349/444ms |

宿主机 5k 组计划 600,000 次，成功 599,674 次，326 次连接重置（0.0543%），各接口 p95 均低于 200ms、p99 均低于 500ms；在该短测中符合错误率 <0.1% 的门槛。8k 组实际请求无错误，但未发出占计划 0.1222%，不算严格通过。短测通过不等同于 30 分钟容量或生产稳定性通过。

上游预算提高到 512 后，网关排队样本均值已为 0，但 API/连接阶段变慢，出现 1,514 个 503；没有保留这项覆盖，最终记录使用 256。不能通过不断扩大队列/连接数证明容量。该轮原始数据和日志样本保留用于审计。

最终版重建 API 后的 5k 预热组仍有 378 个 `CATALOG_BUSY` 和 17 个未发出的请求；保留 Redis 的重启预热不等同于完整冷启动。缓存完全清空、商品批量更新、长尾查询与跨故障域流量尚未达到容量验收。

本地响应副本的宿主机/容器网络两组有相同 API 配置和请求比例，但发压 Node 运行环境、调度位置也有变化，不能将差异全部精确归因于端口转发。它们说明本机入口/发压路径会显著影响测量。90 秒容器网络组仍有 298 个实际请求失败，分页 p95 228ms，尚不满足完整验收门槛。5 秒窗口也没有通过，最终保留默认 1 秒。

## 证据与复现

本地原始证据目录：`var/validation/commerce-catalog-20261030t052150z-05e1/`。包含各组请求统计、Prometheus 与容器 CPU 快照、配置、基线/最终源码和发压脚本。

- `layer-*.txt`：前三层数据；`baseline-*.json`：HTTP 基线。
- `*-metrics.json`：压测中段采样，不能当作整段 CPU 平均值。多进程 API 的 `process_cpu_seconds_total` 不代表所有 worker，因此使用容器合计 CPU 辅助判断。
- `summary.json`：各组摘要；`final-configuration.json`、`measured-haproxy.cfg`：最终实测配置。
- `benchmark-tools/`：本次使用的临时工具副本。控制器写明仓库绝对路径，重跑前需改 `ROOT`，把工具复制到 `/tmp`。`setup` 创建专属环境与随机秘密，`mode` 强制重建 API，`stage` 经宿主机端口压测，`catalog_bridge.py` 经专属容器网络压测，`cleanup` 仅清理该专属项目。不要把这些脚本指向业务数据。
- `source.diff` 是启动时已有工作区差异，不能将其全部归属本次任务；`baseline-source/` 与 `final-source/` 可核对相关文件。

以下四个早期实验因为 Compose 未重启进程、挂载源码未加载，已标记 `invalid_for_change_attribution`，不得用来宣称单项改动收益：`asgi-pool50-cache-4000`、`route-order-cache-4000`、`cache-lookup-4000`、`query-cache-browse-2000`。后续均使用强制重建。Profiler 会改变开销，profile 组不计容量结果。

## 验证边界

`sh scripts/check.sh` 通过：Ruff、格式、mypy 和 compileall。最终代码的一次性服务回归为 57 passed、2 skipped、1 failed（`var/validation/commerce-test-20261030t063152z-60b8b9/`）；唯一失败是 `tests/test_backup.py:97` 写死 `0005_case_fence`，实际迁移头为既有的 `0006_support`。与中途回归结果相同。未修改测试来掩盖失败，也未改实际 `.env`、提交或部署。

压测专属容器、网络、卷和临时秘密已清理，证据目录保留。

最终镜像的 7 项现有 Sentinel 回归通过（`var/validation/commerce-acceptance-20261030t063153z-2b9e91/sentinel.json`），覆盖两组主节点故障、已有客户端恢复、旧主重入、配置重启持久化、失去单个 Sentinel、限流组无副本时拒绝写入及共享额度。该功能恢复验证使用默认部署参数，不是 10k 压力下故障恢复验收。

`uv run --no-sync python scripts/validate_deployment.py` 全部通过：17 个监控目标正常、故障后 Redis 指标恢复、告警到达与解除、单 API 商品查询、滚动重启和 RabbitMQ 队列指标均通过。购买冒烟 252 个请求、10 单、7 笔模拟支付；数据库核对库存与资金差异均为 0。详见同目录 `result.json`。该部署验收的容器、网络、卷和临时秘密也已清理。

本报告的容量结果是本机合成负载，不构成生产验收。正式目标仍需独立发压机、生产尺寸数据、真实访问分布、30 分钟以上 10k 持续测试、2 小时稳定性，以及冷启动、集中失效、商品更新与故障恢复。Next.js 转发入口与 TLS 需要另测；本次没有将它们混算为商品 API 容量。
