# 商品浏览本机固定资源优化：第二轮

日期：2026-10-30。承接 [第一轮记录](catalog-benchmark-2026-10-30.md)。目标是商品浏览 API 持续输入 10,000 RPS，未发出请求也计入失败。

**状态：30 分钟持续测试已完成，稳定 10k 验收未通过。** 成功吞吐约 9,970 RPS，失败及未发出比例为 0.2953%，超过 0.1% 门槛。5 分钟测试整体满足短测门槛，但首分钟未发出比例为 0.1615%；短测结果不能替代长测。

## 固定条件

- 同一台 MacBookPro18,4；Docker 10 CPU、约 7.75 GiB。发压器也在该 Docker 虚拟机内，和服务端竞争资源。没有停止其他项目的容器或调整 Docker 全局资源。
- 隔离项目 `commerce-catalog-20261030t064032z-ca58`：单 PostgreSQL 主库；缓存、限流各有一组 Redis Sentinel；保留 RabbitMQ、worker、监控及网关。所有组使用同一份合成数据：10,000 商品、1,000 用户。
- 最终布局仍是两个普通 API 容器、每个 4 个进程，总计 8 个；另有原来的回调专用 API。
- 每个 API 进程：Redis 每组最多 100 条连接，Uvicorn 并发上限 256，主库池 5、回源并发 4。普通 API 合计主库连接上限 40、回源并发 32、每组 Redis 连接上限 800。
- HAProxy 2 线程，全局连接上限 4096；每个普通 API 上游 `maxconn 256 maxqueue 128`，合计 512 个连接、256 个排队名额。
- 4 个 Node 发压进程，经隔离容器网络访问 HAProxy；每进程最多 256 个 HTTP 连接、512 个在途请求，计划发送落后超过 200ms 或在途满时计为未发出。没有通过增加发压连接或队列来补足数字。
- 比例仍为 50% 详情、20% 首页、10% 搜索、10% 价格筛选、10% 游标分页。有限工作集实际覆盖 50 个详情、10 个搜索词、1 组价格条件、1,000 个游标，不代表任意长尾查询。
- 隔离环境入口 IP 桶放宽至 rate/burst 各 100,000，网关单 IP 入口限制也放宽；仍对每个请求执行共享令牌桶。这用于同一发压 IP，不能作为生产限流建议。其他业务额度使用默认值。
- 最终候选的 HTTP 响应复用为 5 秒；底层查询缓存仍为 15–20 秒，缓存版本仍由 Redis 当前主节点确认。进程内响应条目/字节上限不变。项目默认响应复用配置仍为 1 秒。

延迟从计划发送时刻计到响应正文接收结束。错误预算为计划请求总数的 0.1%，各主要接口 p95 ≤ 200ms、p99 ≤ 500ms；429、503、连接错误和未发出请求均不算成功。完成吞吐除以含尾部排空的实测时间，因此完整发完固定到达率请求时也可能略低于整数目标。

## CPU 与排队证据

复现基线成功约 9,829 RPS，120 万个计划请求中未发出 17,904 个，另有 1 个 `CATALOG_BUSY`。分页 p95 252ms。中段网关日志样本排队均值接近零，而其他时段/组会出现排队，不能把一个时间点当作整段结论。

8 个进程的 cProfile 诊断覆盖 Redis 协议解析和异步读写、HTTP 发送、日志、指标与对象构造。Profiler 改变执行成本，记录的函数耗时含等待和调度影响，不能直接解释为精确 CPU 占比；诊断组不计容量结果。

另一次低侵入日志计时采集了 593,946 次调用：平均墙钟耗时 65.4µs、平均线程 CPU 29.0µs，墙钟 p95 140µs、p99 804µs。日志有成本，但该证据不能把数百毫秒尾延迟全部归因于日志。

一次 40 秒虚拟机采样约为 61.0% 用户态、14.1% 内核态、7.5% softirq、17.4% idle；CPU pressure 的 `some avg10` 约 48–51%。所查 API 容器未触发 CPU quota 节流。空闲比例与调度等待可以同时存在；没有据此证明硬件绝对上限或必须换机器。

## 改动及行为

1. 锁定 `hiredis==3.5.0`，实测容器使用 `_AsyncHiredisParser`。使用其 macOS ARM64/Linux ARM64 wheel，未从源码构建。redis-py 会使用该编译解析器，[官方说明](https://redis.io/docs/latest/develop/clients/redis-py/)；该版本的 [发布说明](https://github.com/redis/hiredis-py/releases/tag/v3.5.0)也已核对。单独加它没有使 HTTP 10k 通过。
2. 结构化日志改用 `WriteLoggerFactory`，每条完整 JSON 连同换行一次写出；保留逐请求日志、字段、请求编号和指标。
3. 本地响应按未带版本的请求 key 索引。没有有效本地条目时直接原子读取版本与响应，不先做额外的版本 GET。等待 Redis 后重新取得本地条目并检查期限，处理并发替换/驱逐。
4. 合并尚未开始执行的目录版本读取。任务开始查询前关闭批次，新到达请求进入下一批；不共享已经开始或完成的查询结果，不引入版本 TTL。取消隔离、后台任务上限和资源退出清理均已实现。
5. 在现有配置范围内将本轮响应复用设为 5 秒。仅扩大响应 JSON 的复用窗口，没有增加底层快照寿命或进程内存上限。
6. HTTP 响应缓存提前让出底层查询的刷新窗口。否则 5 秒复用可能跨过最后 3 秒的提前刷新期，直到过期才回源。中段对照中，简单改 5 秒后目录 miss 从约 0.5/s 升到 26.3/s，后台 refreshed 从约 68.5/s 降到 33.6/s，与该路径相符。最终候选在截止时间前预留 `min(3, cache_query_seconds / 2)` 秒，不在该窗口发布旧快照的 HTTP 响应副本。

版本变化仍切换命名空间；无法确认 Redis 版本时仍不使用本地响应。请求取消不会取消其他请求共用的版本读取。详情/查询缓存不参与报价、订单、库存或授权判断。完整语义见 [目录缓存说明](catalog-cache.md)。

## 对照结果

除注明外均为 10,000 RPS 输入、120 秒、同一有限浏览工作集。下表按累计改动的实际顺序记录，并保留失败实验；单轮对照受缓存阶段和本机调度影响，不是统计显著性的收益估计。

| 组 | 成功 RPS | 未发出 | 已发出失败 | 整体 p95 | 结论 |
|---|---:|---:|---:|---:|---|
| 本轮基线 | 9,829 | 17,904 | 1 | 224ms | 未通过 |
| 仅关闭日志轮转压缩 | 9,855 | 16,726 | 389 | 214ms | 未通过，恢复原配置 |
| 编译 Redis 解析器 | 9,821 | 20,314 | 161 | 216ms | 单独不足以解决瓶颈 |
| 加完整日志一次写出 | 9,961 | 4,436 | 2 | 151ms | 未通过 |
| 加避免重复版本读取 | 9,958 | 4,805 | 4 | 164ms | 未通过 |
| 8 容器各 1 进程，总预算不变 | 9,684 | 37,709 | 0 | 257ms | 未通过，恢复 2×4 |
| 缓存 structlog 绑定对象 | 9,898 | 11,949 | 4 | 205ms | 未通过，移除该设置 |
| 加未发出版本读取合并 | 9,972 | 2,849 | 17 | 123ms | 未通过 |
| 响应复用调到 5 秒 | 9,992 | 236 | 0 | 33ms | 仅短测整体通过 |
| 保留刷新窗口，300 秒 | 9,995 | 1,307 | 0 | 28ms | 整体通过；首分钟未发出 0.1615% |

版本读取合并前后的中段缓存 Redis 命令速率约为 16,410/s 与 11,773/s，限流组均约 50,000/s。Redis 指标包含 Lua 内部命令，不能把该数值直接当作 HTTP RPS。

300 秒组计划 3,000,000 次，成功 2,998,693 次，未发出 1,307 次（0.04357%），实际请求无错误。每分钟未发出分别为 969、338、0、0、0；各分钟各接口 p95 均低于 200ms、p99 均低于 500ms。首分钟未满足更严格的逐分钟 0.1% 错误预算，不以整体均值掩盖。

## 持续测试与验证

30 分钟正式组计划 18,000,000 次，成功 17,946,840 次，未发出 53,060 次，已发出失败 100 次（连接重置），成功约 9,970 RPS，整体 p95/p99 为 72/196ms。失败及未发出占 0.2953%，第 17、18、29 分钟出现明显波动，部分分钟 p95 超过 200ms，未通过稳定 10k 门槛。原始结果为 `r2-stability-1800.json`，异常时段分析为 `long-run-analysis.json`。

其前置 180 秒同强度预热单独保存：计划 1,800,000 次，成功 1,793,349 次，未发出 6,423 次，另有 228 个 `CATALOG_BUSY`。从空闲恢复时的失败不能当作已经解决；正式组用于评估预热后的持续负载。

代码静态检查通过。版本读取合并后的现有回归为 33 passed（限流、缓存回源、观测、事务与恢复），证据在 `var/validation/commerce-test-20261030t072118z-1469dc/`。最终代码审查重跑限流与观测相关现有测试，8 passed。随后移入主线的完整服务回归及工具修复见 [当前优化说明](catalog-performance.md)。没有新增或修改测试文件。

历史发压器保留逐请求样本，并将两种丢弃原因合并，限制了长测根因判断；不能据此证明垃圾回收是本轮掉速原因。已合入主线的工具使用有界直方图并拆分丢弃原因，但尚未用修复后的工具重做 30 分钟容量测试。测试专属容器、网络、卷和临时秘密已清理，原始证据保留。

## 证据与边界

本轮原始证据为 `var/validation/commerce-catalog-20261030t064032z-ca58/`：各组 JSON、逐分钟统计、CPU/Prometheus 快照、日志样本、`profile/`、`log-timing-summary.json`、`round2-code.diff`、`round2-source/`、`source-freeze.json`、`final-configuration.json` 和 `benchmark-tools/`。正式组还记录未发出请求对应的秒数。

`source.diff` 是环境创建时已有的工作区差异，不能全部归属本轮改动。`round2-code.diff` 对源文件使用本轮修改前的副本比较；工作区其他修改没有被覆盖。配置归档不包含隔离环境密码或用户访问令牌。

本轮只验证公开商品 API，经 HAProxy、无 TLS，不包含网页 Next.js 转发、图片、CDN、交易混合流量、任意长尾数据或生产容量。尚不能把热负载结果推广到冷启动、集中失效或高压故障恢复。独立发压机有助于减少竞争，但不是继续本机优化的前置条件。
