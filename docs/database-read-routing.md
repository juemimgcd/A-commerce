# 商品查询读写分离

2026-10-28。读写分离按业务用例选择连接池，不按 HTTP GET/POST 自动路由。

## 路由边界

| 查询 | 数据库 |
|---|---|
| 公开商品列表带搜索词、分类、品牌、属性、非默认价格范围、库存筛选或分页游标的缓存回源 | 副本连接池 |
| 无筛选首页、商品详情的缓存回源 | 主库，沿用现有缓存与失效协议 |
| 分类字典、管理员商品查询 | 主库 |
| 会话、权限、报价、下单、订单查询、支付、退款、库存、任务和幂等结果 | 主库 |

2026-10-30：这些查询增加了独立短期缓存，默认有效 15–20 秒，不返回逻辑过期数据。
分类筛选等查询未命中时仍读取副本。副本查询缓存与主库首页/详情缓存命名空间隔离，
不会用副本旧数据覆盖主库快照。目录版本变化不证明副本已追上主库，展示的价格/库存
可能有复制延迟加缓存时间的滞后；报价与下单在主库重新核验。

## 配置和启用

- `COMMERCE_CATALOG_READ_DATABASE_URL`：可选，指向副本入口，带
  `target_session_attrs=standby`。未配置时沿用单机主库；配置后不因副本故障回退主库。
- `COMMERCE_CATALOG_READ_POOL_SIZE`：每进程独立池上限，默认 5；无额外溢出连接。
- `deploy/compose.ha.yaml` 给两个普通 API 注入 `postgres-read:5432`，回调和 worker 不注入。
  必须加载该 HA 覆盖文件才启用这一部署入口，普通 Compose 不自动变成 HA。
- `postgres-read` 不映射宿主机端口。使用同版本 HAProxy，按连接数把连接分配到健康副本；
  池连接会复用，并非每个 SQL 重新负载均衡。主库入口仍用原有三个地址与 `read-write` 检查。

首次启用需在原 HA 项目的环境和 Compose 文件组合下启动 `postgres-read`，待其健康后重建
两个普通 API 以注入新环境。不会迁移表或修改已有数据。普通服务器 `deploy.sh` 仍是原部署入口。
回退时删除两个 API 的副本 URL 配置并重建进程，恢复单库路由；不要删除数据库卷。

读池设置 `default_transaction_read_only=on`，每次使用显式 `SET TRANSACTION READ ONLY`，
并检查 `pg_is_in_recovery()`，防止复用晋升为主节点的旧池连接。角色错误时丢弃该连接。
HA 示例复用现有应用账号，事务只读不是账号权限隔离；独立只读账号可通过副本 URL 指定，
需要运维在主库配置连接、schema 和 SELECT 权限（含后续表的默认权限）。

## 故障与一致性

HAProxy 使用 Patroni `/replica?lag=16MB`，仅接受健康副本，并检查重放 WAL 相对已知主库
位置的差距。每秒检查，连续两次失败摘除并断开已有连接，连续两次成功恢复。
16MiB 是字节阈值，不是秒级延迟承诺；周期性探测存在窗口，也不保证读到刚写入的数据。
协议依据：[Patroni REST API](https://patroni.readthedocs.io/en/latest/rest_api.html)。

有效查询缓存仍可命中；需要回源而无可用副本、连接/池超时或副本查询失败时，返回 `503 CATALOG_READ_UNAVAILABLE` 与
`Retry-After: 1`。不重放查询、不自动把流量压回主库。主库交易不依赖读入口存活；
应用原有 readiness 仍检查主库，避免副本故障把正常交易 API 从网关一并摘除。
副本晋升与查询同时发生仍有竞态窗口，但事务保持只读，不执行交易决策。

每个普通 API 新增最多 5 条副本连接，两实例共 10 条；滚动重启计入新旧实例重叠。
代理单节点上限 80；连接可能集中到一个剩余副本，预算还应考虑其将来晋升后的负载。
现有 SQL/获取连接时间指标汇总两个池，现有连接数 gauge 仍只反映主库池；
可用 `pg_stat_activity.application_name = 'commerce-catalog-reader'` 区分副本连接。
读入口目前是一个代理容器，代理故障会让分流查询暂不可用，跨主机代理冗余尚未实现。

此变更不改变主库写入和热点锁上限，不表示完成 50,000 RPS 或跨故障域验收。
