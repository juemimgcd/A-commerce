# A-commerce 前端设计与实施计划

日期：2026-10-26。状态：已据此实施 F0–F4，实际交付与验证范围见 [前端实施记录](frontend-implementation.md)。原始设计依据仓库 `95d2bd4` 的接口和业务规则；F5 仍按 M7 后续实施。

首版交付中文数码配件商城与商家后台，让买家完成选品、确认报价、付款、追踪订单和售后，让商家完成商品维护、履约与异常处理。采用浅色、商品图片优先、规格易比较的方向；先设计完整购买路径，再逐步增加管理能力。

制定计划时项目只有 FastAPI 后端，没有前端工程、组件或设计 token。本计划沿用单店、单仓、CNY 的范围；普通购买独立可用，pi 助手仍按 [M7](mvp-plan.md) 在后端验收后接入。前端交付不代替真实支付、生产部署或 1 万在线容量验收。

## 1. 用户与设计目标

| 使用者 | 要解决的问题 | 页面应帮助完成的主要动作 |
|---|---|---|
| 买家 | 配件是否匹配、实际付多少钱、付款与退款是否完成 | 选定具体规格，确认后端报价并购买 |
| 商品运营 | 商品、规格、价格和库存容易改错 | 核对变更内容后保存 |
| 履约与售后人员 | 不同订单阶段允许的操作不同 | 处理当前待办，保留操作原因和结果 |
| 审计与身份管理员 | 资金异常、员工权限和敏感操作需要追溯 | 查看证据，执行权限允许的处理 |

默认中文界面、商城优先适配手机、后台优先适配桌面，品牌名称暂用 A-commerce。实际商品图片、分类、价格和政策取自后端；缺少的品牌素材与商家信息列为交付输入。

页面质量首先看四件事：能否找到匹配规格，确认前是否看清总价，交易结果是否准确，异常后是否有明确的下一步。后续记录选品至报价、报价至订单创建、支付确认等分段完成率，先建立基线，不预设提升成绩。

### 商家后台

| 导航分组 | 路径 | 主要工作 | 权限与阶段 |
|---|---|---|---|
| 商品与库存 | `/admin/products`、`/admin/inventory` | 分类、商品、SKU、媒体、上下架、库存调整与流水 | `catalog`；F3 |
| 订单履约 | `/admin/orders`、`/admin/orders/[id]` | 状态筛选、拣货、发货、履约详情 | `fulfillment`；F3 |
| 售后与退款 | `/admin/returns`、`/admin/refunds` | 审核、收件、验收、查看退款结果 | `aftersales`；F3 |
| 经营与对账 | `/admin/reports`、`/admin/reconciliations` | 资金日报、商品排行、导出、差异复核 | 按各接口权限；F4 |
| 异常与审计 | `/admin/operations`、`/admin/audits` | 异常任务、隔离消息、操作记录与受控重放 | 按各接口权限；F4 |

## 3. 重点页面结构

### 商城首页与商品列表

首页采用简短选购引导、分类、商品网格、购物帮助的顺序。商品尽早进入首屏，搜索始终易找到。首版使用已有目录入口；专题、精选排序和推荐算法需另有数据支持。

首页文案草案：

- 标题：**按规格，找到合适的数码配件**。
- 说明：从接口、功率和预算开始筛选，核对规格、运费与总价后再下单。
- 主要按钮：**浏览全部商品**。
- 事实说明：运费与总价以结算时生成的报价为准。

商品列表桌面左侧放筛选，右侧放结果与已选条件；手机筛选收进抽屉。条件写入 URL，返回列表时恢复筛选和位置。当前 API 支持游标分页，界面使用“加载更多”；没有总条数、全局价格排序与销量排序时不展示对应控件。品牌和属性选项需来自完整的筛选元数据，不能把当前一页的数据当成全目录选项。

商品条目只突出图片、名称、关键规格和价格。价格取有效且匹配当前条件的 SKU；展示最低价时写明“起”，进入详情选择规格后展示准确价格。无图使用明确的“暂无商品图片”状态，不用不相干图片替代。

### 商品详情

桌面约 7:5 分栏：左侧主图与缩略图，右侧名称、品牌、价格、规格选择、数量、可售状态和“加入购物车”。下方是规格表、商品说明和配送售后说明。手机改为单列，购买操作固定在底部安全区内，正文预留空间。

SKU 指具体可购买的规格组合。单一有效 SKU 可以预选；多规格商品必须显示明确选中项，无效组合不可选。缺货、下架和当前规格不可用分别说明。图片支持查看细节，参数表优先展示接口、功率等实际属性；不生成没有商品数据支持的兼容性承诺、评分或销量。

### 购物车与结算

```text
桌面结算
┌─────────────────────────────┬────────────────────┐
│ 收货地址                    │ 商品金额           │
│ 商品名称 / 规格 / 数量       │ 运费               │
│ 配送与售后规则               │ 应付总额           │
│ 报价变化或缺货的具体提示      │ 报价有效期         │
│                             │ 确认并创建订单     │
└─────────────────────────────┴────────────────────┘
手机：地址 → 商品 → 规则 → 金额明细 → 确认按钮
```

购物车标注无效商品与库存变化，数量修改有保存中、失败与重试状态。后端购物车最多 100 个 SKU，单次报价最多 50 个 SKU，每行最多 99 件；达到限制时明确提示，不静默截断。

结算分“编辑购买内容”和“查看报价并确认”两个状态。选择地址、调整数量后重新获取报价；只使用后端返回的运费和总价。新旧报价不同时展示差异并再次确认。购物车不占库存，生成报价也不代表库存已预留；订单创建成功后才进入待支付。

### 订单与售后

订单详情先显示当前结果与可执行操作，再显示商品成交快照、金额、地址和时间线。订单状态、支付状态、履约状态分别呈现；部分退款单独列已退款金额和处理中金额，不覆盖原履约历史。

售后先读取可申请的订单行、数量和单价，再让用户填写原因。寄回信息、商家收件地址、验收结果与退款进度放在同一详情页。验收完成只表示实物处理完成，退款成功必须有资金结果支持。

### 后台工作列表与详情

桌面使用约 240px 侧栏、页标题与主要动作、筛选工具栏、明细表格。选择一行可以快速查看摘要，完整编辑进入有独立 URL 的详情页，刷新后仍可定位。避免每个字段单独放大卡片。

订单详情按商品与收件信息、资金状态、履约操作、审计记录分区。发货前展示物流公司与单号确认；库存调整展示变化前后数量并要求原因；敏感操作需要重新登录时保留表单草稿，登录后重新读取状态并由用户再次触发。

## 4. 视觉与组件规范

采用“冷白底、石墨正文、钴蓝主要操作”的单一浅色系统。商城通过图片和留白区分商品，后台通过对齐、表格和状态层级提升扫描效率。

参考本机设计目录的 Shopify 交易页面信息层次，以及 Linear 对强调色、细边框和内容层级的克制使用；两份资料主要描述品牌网站，不视为现成后台规范。只借鉴兼容的原则，所有页面使用 A-commerce 自己的 token。

| 项目 | 建议规范 |
|---|---|
| 背景与表面 | `canvas #F7F8FA`、`surface #FFFFFF`、`border #D8DEE8`；纯色背景 |
| 文字 | `text #172033`、`muted #526079`；金额和关键信息优先保证可读性 |
| 主要操作 | `primary #1D4ED8`、`hover #1E40AF`；用于主要按钮、选中项和焦点 |
| 状态 | 成功 `#166534`、处理中 `#92400E`、错误 `#B91C1C`，配文字与图标 |
| 字体 | Geist 为主，中文使用 PingFang SC / Noto Sans CJK SC 系统回退；400、500、600 字重 |
| 字号与行高 | 标题 30/36、24/32；小标题 20/28；正文和主按钮 16/24；辅助信息 14/20；标签 12/16 |
| 间距 | 使用 4、8、12、16、24、32、48、64px 等技能规定档位；组件内距通常 16 或 24px |
| 圆角 | 小标签 4px，输入框和按钮 8px，主要容器 12px；嵌套圆角按间距递减 |
| 按钮 | 常规内距纵向 8px、横向 12px；触控高度至少 48px；每个任务区一个主要操作 |
| 图标 | Phosphor，同一线条风格；图标按钮提供可读名称 |
| 深度与动效 | 优先边框和表面区分层级；抽屉、菜单使用 `cubic-bezier(0.32,0.72,0,1)`，减少动态效果时关闭位移动画 |

交易内容首屏立即可见，金额、错误和确认按钮不依赖滚动动画出现。标题使用平衡换行，中文文案不强塞英文断词。重要文字不使用低透明度灰色。

先建立并统一复用以下组件：Button、Field、Select、Dialog、Drawer、Tabs、Table、StatusBadge、Money、ProductTile、SkuSelector、QuantityInput、AddressPicker、OrderSummary、StatusTimeline、AsyncState。具体交互组件库在 F0 固定一种，封装在同一 UI 层；业务页面不重复维护按钮和表单样式。

每个组件交付默认、hover、active、focus-visible、disabled、loading 状态；数据区域另有初次加载、空结果、局部失败和保留旧数据的刷新状态。首屏加载使用结构相符的骨架；提交时显示“正在创建订单”等具体进度，避免把整个表单替换为空白。

## 5. 交易状态与恢复设计

| 后端结果或场景 | 页面行为 | 后续操作 |
|---|---|---|
| `QUOTE_EXPIRED` / `QUOTE_STALE` | 报价已失效，保留购买意向并指出变化 | 获取新报价，再次确认 |
| `OUT_OF_STOCK` / `PRODUCT_UNAVAILABLE` | 明确本次订单未创建，返回检查商品 | 修改数量或规格；不擅自替换商品 |
| 下单请求超时 | 显示“正在确认订单结果” | 用原幂等键查询 `/customer/order-requests/{key}`；必要时原键原参数重试 |
| `pending_payment` + `preparing` | 订单已创建，支付入口准备中 | 有界查询，不显示已付款 |
| 支付 `pending` | 显示支付入口、金额和截止时间 | 用户主动支付 |
| 支付 `unknown` / 订单 `closing` | 显示“支付结果核对中”或“正在关闭订单” | 查询服务端结果；不引导重复支付 |
| `cancelled` 且退款处理中 | 显示取消完成，退款仍在处理 | 保留金额和查询入口 |
| `ORDER_STATE_CONFLICT` / `RETURN_STATE_CONFLICT` | 当前状态已变化 | 刷新详情并解释当前可执行动作 |
| `RECENT_AUTH_REQUIRED` | 要求重新登录，保留非敏感草稿 | 重新核对状态后由用户再次确认 |
| `CHECKOUT_PAUSED` / 429 | 说明暂时无法受理，保留输入 | 有 `Retry-After` 时遵循，否则退避，提供受控重试 |
| 401 / 资源不可访问 | 失效会话重新登录；404 给出不可访问说明 | 不将所有 404 都解释为资源已删除 |
| 事件游标过期 410 | 标注状态同步中 | 创建并读取完整快照，再从 `through_sequence` 继续拉取 |

订单提交前生成并保存稳定的 `Idempotency-Key`，与账号、报价和请求参数绑定。刷新页面后仍能查询未决请求；本地仅保留必要标识，不保存密码、Token 或完整地址。一次查询返回未找到不证明原请求永远不会提交；不得因此换键、换报价自动再下单。

取消、发货等请求携带当前 `expected_version`。冲突时展示最新状态，不静默覆盖。退货申请也使用稳定幂等键；请求结果未知时不新增另一份申请。

倒计时从服务端 `expires_at` 推导，只用于提示；到零后读取实际状态，不在浏览器自行关闭订单。初期只轮询当前可见的支付或订单页，设置退避、总等待上限、离线暂停和手动刷新；后台标签不持续轮询。上限到达后保留“仍在核对”，不将其判定为失败。

支付接口当前返回本站 `simulate-payment` 路径，属于受认证保护的模拟操作，不是可直接跳转的外部收银台。开发演示明确标注模拟环境；真实沙箱需要独立接入和验证。未来支付返回页也必须以订单查询结果为准。

## 6. 接口对接与前置缺口

接口前缀统一为 `/api/v1`。以下“已有”只表示代码中存在，不表示前端联调或生产验收已经通过。

| 页面能力 | 已有接口或契约 |
|---|---|
| 浏览与详情 | `GET /customer/categories`、`/customer/products`、`/customer/products/{id}`、`/customer/products/{id}/media` |
| 账号与地址 | `/customer/auth/*`、`GET /customer/profile`、`/customer/addresses`、`/customer/sessions` |
| 购物车与收藏 | `/customer/cart`、`PUT /customer/cart/items/{sku_id}`、`/customer/favorites` |
| 报价与订单 | `POST /customer/quotes`、`POST /customer/orders`、`GET /customer/order-requests/{key}` |
| 支付与履约查询 | `/customer/orders/{id}`，及该订单下的 `/payment-session`、`/shipment`、`/history` 子路径 |
| 售后 | `/customer/orders/{id}/return-options`、`POST /customer/orders/{id}/returns`、`/customer/returns`、`/customer/returns/{id}/ship` |
| 通知与恢复 | `/customer/notifications`、`/customer/notification-preferences`、`/customer/events`、`/customer/event-snapshots` |
| 后台 | `admin.py` 与 `operations.py` 中商品、库存、订单、售后、报表、对账、员工及审计接口 |

### 相应阶段联调前必须解决

| 缺口 | 制定计划时的事实 | 计划处理 |
|---|---|---|
| 商品图片与购物车展示 | `ProductOut` 没有封面；`CartOut` 没有商品 ID、规格和媒体引用 | F1/F2 增加最小展示字段；列表批量提供封面引用，避免逐商品查询图片列表 |
| 报价规格快照 | 报价行有标题、数量和价格，没有规格属性 | F2 补入报价规格快照；确认页不依赖可变商品缓存解释所买规格 |
| 报价刷新与购物车清理 | 没有查询单个报价的 GET；下单服务不自动清理购物车 | 未提交时刷新重新报价并确认；已提交未决时先恢复原请求。明确成交行清理规则，避免清空其他商品或覆盖其他标签页修改 |
| 管理员自身权限 | 登录只返回 Token；没有自身资料/权限接口，员工列表要求 `identity` | F3 增加自身资料、权限和当前会话接口；不能用员工列表替代，也不能从 Token 推测权限 |
| 后台商品与库存读取 | 有商品列表和写接口，没有按 ID 的管理详情；低库存列表不能代替完整库存查询 | F3 增加管理详情、分页库存及单 SKU 库存读取；支持刷新编辑页和查看占用量 |
| 未上架商品媒体 | 现有公开媒体读取要求商品已上架 | F3 增加受 `catalog` 权限保护的媒体预览，满足草稿商品编辑 |
| 售后详情与资金结果 | `ReturnOut` 缺申请行、数量、金额、时间和退款状态；订单没有政策/售后截止时间输出 | F3 补足订单政策摘要、售后明细和买家可读退款摘要；金额由后端计算 |
| 寄回信息 | 现有退货详情没有商家收件地址 | F3 明确商家地址配置及返回契约；未配置时不能开放填写虚构地址的寄回流程 |
| 商店能力与配置读取 | 无前端能力描述；运费规则只有写入口，没有列表读取 | F2 明确可信环境配置；F4 补规则读取。支付模式、邮件启用状态必须可判断 |

### 按现有能力收敛首版

- 商品筛选没有完整选项元数据和排序契约，先保留可用条件；全局排序、全量品牌选项后续补接口。
- 地址目前支持新增和编辑，不设计可点击的删除、默认地址功能；地区值与运费规则精确匹配，地区选项与规则必须统一。
- 商品媒体目前只有上传与读取，不承诺拖动排序、设主图或删除；如纳入设计，需要对应写接口和权限。
- 售后验收只有整份申请的 `resellable` 布尔值，不能画成逐行、逐件验收后直接调用现有接口。
- 订单查询没有通用关键词搜索；可输入完整订单 ID 定位，其他筛选只使用已支持的状态和时间条件。
- 会话没有设备名、地点或当前设备标记，不编造设备列表。通知也不以当前页条数冒充全量未读数。
- 导入目前是 JSON 商品批次，导出是资金日报 CSV；通用 Excel 导入和任意表导出另行定义。

## 7. 前端工程建议

仓库已新增独立 `frontend/`，采用 Next.js App Router、React、TypeScript 与原生 CSS 设计 token。商城与后台放在同一前端工程中，通过路由、布局、会话和查询缓存分离。公开商品页服务端输出主要内容，购物车、结算与后台使用客户端交互。版本和直接依赖精确锁定，实际命令见前端 README。

Next.js 的 Route Handlers 可作为浏览器到 FastAPI 的薄转发层，只负责会话、接口白名单和数据转交；交易规则继续由 FastAPI 执行。服务端渲染直接通过服务端客户端访问 FastAPI，不绕回自己的 HTTP 转发接口。[Next.js 官方 BFF 指南](https://nextjs.org/docs/app/guides/backend-for-frontend)

会话复用后端可撤销 Token，浏览器通过服务端设置的 `HttpOnly`、`Secure`、`SameSite` Cookie 使用；买家与员工会话分别命名和路由。写请求增加来源校验与 CSRF 防护，注销同时撤销后端会话并清除 Cookie。角色和资源归属始终由 FastAPI 验证。[Next.js 官方认证指南](https://nextjs.org/docs/app/guides/authentication)

数据请求建议统一使用类型化 API 客户端，类型从后端 OpenAPI 生成；关键交易响应另做运行时校验。TanStack Query 管理客户端读取、失效刷新和局部加载，显式设置刷新与重试规则，避免采用默认策略造成重复查询。交易写入不统一自动重试，按第 5 节恢复。[TanStack Query 官方默认行为说明](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

工程边界：

- 金额保持整数分，展示时格式化为人民币；前端不重算最终应付、可退款金额或运费政策。
- 日期使用带时区值；界面默认北京时间并明确报表日期口径。净收款不标成利润。
- 统一处理错误码、`request_id`、`Retry-After`、鉴权失效和未知状态；保留用户可复制的请求编号。
- 当前 API 统一返回 `Cache-Control: no-store`。首版不擅自增加共享响应缓存；商品图片/目录缓存另定失效规则，私有与交易数据不进入公共缓存。
- 网关和转发层必须一起验证可信来源 IP，避免所有浏览器请求被算成一个前端服务器 IP；浏览器自报身份或转发头不能替代后端身份。
- UI 层、商城业务、后台业务、API 契约分别组织；首版不额外引入微前端、独立前端数据库或第二套订单状态机。

## 8. 响应式、可访问性与内容交付

| 视口 | 商城 | 商家后台 |
|---|---|---|
| 手机 360–767px | 商品网格按内容放 1–2 列；筛选抽屉；详情与结算单列；购买栏适配安全区 | 导航抽屉；列表保留关键字段；完整操作在独立详情页 |
| 平板 768–1023px | 商品通常 3 列；详情按空间切换单/双列；结算摘要不能挤压输入区 | 收起侧栏；次要列收进详情，不缩小正文凑宽度 |
| 桌面 ≥1024px | 内容宽度约 1280px；商品通常 4 列；详情与结算双列 | 固定侧栏与明细表格；宽表在容器内滚动 |

所有表单有真实 label、字段级错误和错误摘要；对话框支持焦点管理、Esc 关闭和焦点返回。页面提供跳转主内容、语义导航、清晰标题、可见键盘焦点。状态不能只靠颜色，动态结果有适当读屏提示，重要金额不会被 sticky 区域遮挡。

公开商品内容在 JavaScript 未完成加载时仍能阅读，交易提交区明确说明不可交互状态。尊重减少动态效果设置；图片有尺寸、替代文字和失败状态。浏览器验收覆盖 Chrome 与 Safari，尤其检查中文输入、抽屉焦点、触屏键盘和底部安全区。

公开发布时，真实首页、商品和规范分类页可索引；搜索组合、购物车、结算、个人页和后台不索引。预览与模拟环境整体不索引。补齐页面标题、描述、canonical、站点图、favicon、分享图和 404；结构化数据只使用真实价格与库存，不添加虚构评价。

上线前需要实际商家名称、联系渠道、配送范围、售后与退货地址、隐私和条款内容。购物帮助至少解释规格如何选择、总价如何确定、支付结果如何确认、如何取消和申请退货。演示售后天数和运费规则以服务端快照为准，不直接写成正式商业承诺。

| 阶段 | 交付 | 完成条件 |
|---|---|---|

| F3 售后与基础管理 | 退货、寄回、验收与退款展示；商品/库存、拣货/发货、权限导航 | 买家与商家能完成一次部分退货；退款与库存结果分别核对；不同权限和重新登录流程可用 |
| F4 运营与发布完善 | 收藏、比较、通知、会话、报表、对账、审计、员工、导入导出、政策内容 | 所有入口有实际能力；响应式与可访问性检查完成；形成问题清单和发布记录 |
| F5 助手入口 | M7 条件满足后，独立授权、可信动作确认、撤销和结果展示 | 普通购买继续可用；确认摘要来自后端，模型不能替用户批准或付款 |

实施依赖：F0 → F1 → F2 → F3 → F4。F5 另依赖 M7 的后端授权与适配器契约。首个可演示目标是 F2；完整前端交付目标是 F4，生产发布仍受外部集成和后端验收门槛约束。

每阶段按页面逐项验收，至少包含：

1. 在 390px、820px、1440px 检查真实浏览器布局；另检查 360px、200% 缩放、键盘操作与减少动态效果。
2. 核对加载、空、错误、失效会话、权限变化和网络中断；刷新后能恢复筛选与未决订单。
3. 在隔离联调环境覆盖正常购买、缺货、变价、报价过期、重复提交、支付核对、取消/发货竞争、部分退货。
4. 前端工程建立后运行其已定义的 lint、typecheck 和相关项目检查；浏览器网络记录检查请求扇出、轮询停止和错误恢复。加载与交互性能记录环境和实测值，不预写成绩。
5. 保存界面截图、接口状态、观察到的业务结果与未解决问题。遵守项目约定，仅运行已有测试；新增或修改测试须有当前请求的明确授权。
