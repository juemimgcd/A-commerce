# 商品浏览优化与压测工具

公开商品浏览使用参数完整的查询缓存，以及最多 5 秒的已校验 JSON 响应复用。默认响应复用为 1 秒，0 可关闭。缓存只用于展示；报价、订单和授权继续核验数据库事实。

## 应用行为

- 搜索、分类、品牌、属性、价格、库存筛选与分页使用独立查询 key，包含所有过滤参数，默认保留 15–20 秒，无额外旧值窗口。
- 查询在最后 `min(3, cache_query_seconds / 2)` 秒尝试后台刷新；HTTP 响应缓存提前让出该窗口，不延长底层数据截止时间。
- 仅公开商品列表与 UUID 详情的 200 JSON 响应可复用，错误、媒体、私有接口和带 Set-Cookie 的响应不进入缓存。每个响应最多 64 KiB；进程内 LRU 最多 1024 项、正文总计 8 MiB。
- 每个请求仍执行共享入口限流。有效本地命中需要 Redis 当前版本查询确认；无法确认时不返回本地响应。本地未命中直接原子读取版本与响应快照。
- 尚未开始的版本查询可合并；开始查询前关闭批次，之后到达的请求进入下一批。没有版本 TTL，单个请求取消不会取消其他等待者共用的查询。后台任务数量有界，退出时先取消并等待，再关闭 Redis。
- Redis 默认每进程每组连接上限 50，池满最多等待 50ms；限流调用仍有 350ms 总预算。只在 NOSCRIPT 时重发脚本，不重放结果不确定的扣减。
- HTTP 请求编号、日志和指标由直接 ASGI 中间件处理。日志逐条完整写出；应用内耗时在响应头开始时记录，不包含完整正文传输。

本 PR 基于主分支的单主库目录读取，不包含本地工作区尚未提交的副本路由部署。

## 固定到达率发压

使用已有的隔离数据集（`scripts/seed_load.py` 输出的 JSON），只允许访问本机 loopback 地址；不要使用业务数据集。脚本要求 Node.js，未增加 npm 依赖。

```sh
mkdir -p var/catalog-benchmark
node scripts/catalog_load.mjs http://127.0.0.1:58000 dataset.json browse 10000 1800 var/catalog-benchmark/result.json 4
```

位置参数为入口、数据集、请求分布、总 RPS、时长（秒）、输出路径、发压进程数（默认 4）。总 RPS 必须是可被进程数整除的正整数。`browse` 为 50% 详情、20% 首页、10% 搜索、10% 价格筛选、10% 游标分页，采用与历史测试相同的请求索引规则。

每进程最多 256 个 HTTP 连接、512 个在途请求；计划发送落后超过 200ms 或在途已满时丢弃。总计 `dropped` 保持原口径，同时输出三个互斥原因：`inflight_full`、`scheduler_late`、`both`，三者之和等于总丢弃数。`both` 表示两个条件同时成立，不证明其中某一个是根因。

工具还记录 Agent 连接等待/连接数峰值、事件循环 p99/最大延迟，以及按 30 秒采样并在结束时补采的最大 RSS。它们用于定位发压端开销，不能替代服务端排队与 CPU 时间线。

延迟从计划发送时间算到响应正文结束，包含发送调度落后与客户端连接等待。统计使用 1ms 向上取整的有界直方图，不再保存每次请求的浮点样本。超过 60 秒的观测进入溢出桶；`histogram_overflow` 保留数量，若分位数落入溢出桶则返回 null，不能当作延迟通过。

每分钟的直方图在该窗口全部在途请求结束后写入 `result.json.partN.json.windowM.json`，随后释放内存中的窗口明细。父进程从文件逐窗口合并直方图，按累计频数计算分位数，不平均子进程 p95。长期统计元数据随分钟数增长，明细不随请求总数累积。复核时应保留所有 part、window 和 progress 文件。

退出码 0 只表示发压流程完成。容量判断必须检查 planned、success、dropped、错误状态、各接口延迟和逐分钟结果；429、503、连接错误和未发出请求均不算成功。

## 已测结果与限制

2026-10-30 的历史测试在本机 Docker 10 CPU、约 7.75 GiB 内进行，发压器和服务端共用资源。8 个 API 进程、两个容器，5 秒响应复用；合成数据 10,000 商品、1,000 用户。有限浏览工作集覆盖 50 个详情、10 个搜索词、1 组价格筛选和 1,000 个游标，不代表任意长尾流量。

| 测试 | 计划请求 | 成功 | 未发出 | 已发出失败 | 成功 RPS | 整体 p95/p99 |
|---|---:|---:|---:|---:|---:|---:|
| 5 分钟 | 3,000,000 | 2,998,693 | 1,307 | 0 | 9,995 | 28/102ms |
| 30 分钟 | 18,000,000 | 17,946,840 | 53,060 | 100 | 9,970 | 72/196ms |

**30 分钟未通过稳定 10k 验收**：失败及未发出比例为 0.2953%，超过 0.1%；部分分钟 p95 超过 200ms。历史测试使用修复前的逐请求样本统计器，两项工具修复不应被解释为已经改善吞吐。应用代码随后移入最新 main，并排除了未提交的副本路由配置；这不是对 PR 最终提交的容量认证。

历史原始证据保留在本地 `var/validation/commerce-catalog-20261030t064032z-ca58/`（gitignored）。新的功能性发压验证仅检查工具输出和窗口合并，不构成 30 分钟容量复测。

本次工具验证在原有隔离环境经宿主机端口运行：1,000 RPS、65 秒共 65,000 次全部成功，形成 60 秒与 5 秒两个完整统计窗口；另一次 10,000 RPS、15 秒运行中记录 4,453 次 `inflight_full`，Agent 等待队列峰值每进程 256，所有丢弃均保留在总失败口径中。两组直方图均无溢出。该短时高压组仍有 503/连接错误，不能当作容量通过。

移入最新 main 后，`sh scripts/check.sh`、依赖审计及完整现有真实服务回归通过（58 passed、2 skipped，启用 ResourceWarning 错误检查）。没有新增或修改测试文件。既有回归未完整覆盖版本合并的所有取消、过期与切主组合。

本次范围不含 Next.js 转发、TLS、图片、CDN、交易混合流量或生产验收。冷启动、集中失效、商品更新和高压故障恢复仍需验证。测试文件按项目约定保持不变。
